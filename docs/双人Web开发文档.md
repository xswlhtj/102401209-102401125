## 1. 项目目标

本项目把第一次结对作业的校园失物招领原型实现为可运行的 Web 应用。

核心流程为：

```text
发布信息 -> 浏览或搜索 -> 查看详情 -> 联系发布者 -> 发布者修改状态
```

本次选择 **Web** 形式，统一使用 Google Chrome 开发和测试。项目采用 HTML、CSS 和原生 JavaScript，不开发复杂后台、实名认证、即时聊天和地图定位。

## 2. 最终技术方案

| 内容 | 选择 |
| --- | --- |
| 页面 | HTML5 |
| 样式 | CSS3、Flexbox、Grid、CSS变量 |
| 程序逻辑 | 原生JavaScript |
| 页面导航 | Hash路由，如 `#/home`、`#/detail/item-001` |
| 数据保存 | `localStorage` 和内置演示数据 |
| 单元测试 | Vitest |
| 协作方式 | GitHub、Fork、功能分支和Pull Request |

网页本身不依赖 npm 和构建工具。npm 只用来安装、运行 Vitest。

**浏览器加载约定：** 本项目保持无构建、直接打开HTML的方案。业务脚本使用普通 `<script defer src="…"></script>`，按基础工具、数据、服务、UI、页面、路由、入口的依赖顺序加载；不使用 `async`、浏览器端 `type="module"` 或 `fetch()` 读取本地JSON。种子数据放在JS文件中。分目录本身没有问题，限制来自具体加载方式。

各脚本用函数作用域隔离内部变量，通过 `globalThis.LostFound` 暴露接口。业务脚本加载时只定义函数，不直接访问DOM或读取存储；由 `app.js` 初始化。测试可用Vitest的 `import` 加载同一份业务脚本并调用该命名空间，不能另写一套业务实现。浏览器加载限制不等于测试文件也不能使用模块。

**使用范围：** 当前为单机演示版，不支持不同电脑之间共享发布数据。`ownerId`用于演示归属判断，界面和服务层都要检查，但不等同于服务器身份认证或安全权限控制。作业未指定必须采用后端，也未明确承诺单机方案可获得全部功能分；README应如实说明范围，若班级后续要求真实多人共享，则需增加服务端。

## 3. 功能与负责人

### 3.1 核心功能

| --- | --- | --- | --- |

### 3.2 状态规则

| 类型 | 初始状态 | 完成状态 |
| --- | --- | --- |
| 寻物 | 寻找中 | 已找到 |
| 招领 | 待认领 | 已归还 |

第一次原型中出现过“已找回”，第二次项目全部统一为“已找到”。

### 3.3 附加特点（核心功能通过后实现）

- **类别组合筛选（F04）：** 在关键词和类型基础上增加类别条件，A负责算法，B负责控件。类别与发布表单共用列表，不另加地点面板。
- **一键复制（F06）：** B负责复制与失败后手动复制提示。查看联系方式是核心要求，自动复制才是附加便利。

两项用于附加特点展示，不是老师指定必须实现的功能，也不保证仅凭数量获得满分。

## 5. 页面与业务要求

### 5.1 首页

- 展示多条寻物和招领记录，并能使用鼠标滚轮浏览。
- 卡片显示图片、名称、类型、状态、地点和日期。
- 底部导航不能遮挡最后一张卡片。
- 点击不同记录进入各自的详情页。

### 5.2 发布页面

- 寻物和招领共用一套表单，通过标签切换类型。
- 表单字段包括名称、类别、日期、地点、描述和联系方式。
- 输入错误时在对应字段附近提示，并聚焦第一个错误。
- 保存过程中禁止重复点击。
- 发布成功后，新记录能在首页和“我的发布”中看到。

### 5.3 搜索页面

- 搜索框默认显示提示信息，不预填“校园卡”。
- 支持键盘输入、Enter搜索和按钮搜索。
- 支持全部、寻物和招领筛选。
- 附加类别筛选与关键词、类型同时生效，“全部类别”不限制结果，清除条件一次清空三项。
- 关键词至少匹配物品名称，可同时匹配类别、地点和描述。
- 没有结果时显示提示和“清除条件”按钮。

### 5.4 详情页面

- 根据记录ID读取数据，显示与列表相同的信息。
- 从首页进入就返回首页，从搜索进入就返回原搜索结果。
- 未完成记录可以复制联系方式。
- 点击复制后优先调用 `navigator.clipboard.writeText()`，只有成功才提示“已复制”；接口不存在或调用失败时展示可选中的完整文本，提示用Ctrl+C手动复制。不把复制失败误报为成功。
- 已完成记录仍可查看，但不继续引导联系。
- 记录不存在时显示友好错误页面。

### 5.5 我的发布与状态修改

- 只显示当前演示用户发布的记录。
- 未完成记录显示“修改状态”，完成记录只显示详情。
- 修改前显示确认框，保存中禁止重复操作。
- 寻物成功提示：“该信息已标记为‘已找到’”。
- 招领成功提示：“该信息已标记为‘已归还’”。
- 更新后首页、搜索、详情和我的发布必须同步。
- 服务层按“记录存在 -> 当前演示用户为发布者 -> 状态为active”的顺序校验；重复关闭或非法ID应拒绝，旧数据保持不变。

## 6. 数据设计

每条信息使用以下结构：

```js
{
  id: "item-001",
  ownerId: "demo-user-001",
  type: "lost",                 // lost 或 found
  name: "黑色蓝牙耳机",
  category: "电子设备",
  eventDate: "2026-09-26",
  location: "东三教学楼",
  description: "充电盒外侧有轻微划痕",
  image: "assets/images/earbuds.jpg",
  contactType: "QQ",
  contactValue: "123456789",
  status: "active",             // active 或 closed
  createdAt: "2026-09-26T14:30:00+08:00",
  updatedAt: "2026-09-26T14:30:00+08:00"
}
```

数据层只保存 `active` 和 `closed`，由统一函数转换为中文：

```text
lost  + active = 寻找中
lost  + closed = 已找到
found + active = 待认领
found + closed = 已归还
```

所有页面都通过数据服务读取信息，页面代码不能各自保存一份静态物品数据。

**接口先约定再分工：** A提供 `list(filters)`、`getById(id)`、`create(formData)`、`closeItem(id, actorId)`；统一返回 `{ ok: true, data }` 或 `{ ok: false, error: { code, message } }`。B负责页面调用和反馈；A完成持久化后才返回成功，B随后重新查询并渲染，解决F09与F10的交接。

**存储边界：** `file://`下的localStorage行为不是跨浏览器保证。A应捕获访问、解析和写入异常，失败时返回错误、保持旧记录；B保留表单并提示失败。验收要在实际Chrome版本、相同文件路径下测试关闭重开后的数据。换电脑、换浏览器、清除站点数据或移动文件后，不承诺恢复原记录；不能把仅存在内存中的结果提示为“已保存”。

## 9. 怎么运行

### 9.1 运行网页

1. 下载或克隆完整项目文件夹。
2. 找到根目录的 `index.html`。
3. 右键选择使用 Google Chrome 打开。
4. 网页不需要安装数据库，也不要求启动服务器。

必须在一台没有配置开发环境的电脑上验证一次，确保直接打开能够正常显示和操作。

最终验收必须使用地址栏为 `file://` 的直接打开方式，检查脚本、图片、刷新后数据和复制功能；仅在Live Server上通过不能代替此检查。该方式是本项目选定的交付约束；作业评分规则也提到额外环境需说明清楚，不能据此断言所有使用本地服务器的方案都违规。

### 9.2 运行单元测试

成员A先配置Vitest开发依赖，并将 `package.json` 的 `scripts.test` 设为 `vitest run`；提交锁文件，在README写明已验证的Node.js和Vitest版本。其余成员在安装对应Node.js后，进入含 `package.json` 的项目根目录执行：

```bash
npm install
```

以后运行全部测试：

```bash
npm test
```

Vitest 只用于自动测试，不影响用户直接打开网页。

单元测试默认采用Node环境，通过注入内存存储替身测试服务，不假定有 `window` 或 `localStorage`。每个用例重置存储和演示用户；T03固定“今天”的时钟。浏览器中的复制权限、页面布局和真实存储行为仍由Chrome实测。

## 10. 单元测试方案

### 10.1 为什么选择Vitest

- 适合JavaScript项目，语法简单。
- 测试结果清楚，便于截图和写测试报告。
- 可以模拟 `localStorage`。
- 支持自动运行所有测试，满足作业对自动化单元测试的要求。
- 后续如果增加模块，容易继续补充测试。

### 10.2 单元测试和功能测试的区别

**单元测试**检查独立函数或服务是否正确，例如输入校验、搜索结果和状态转换。不同功能的输入和判断规则不同，所以测试内容也不同，但不需要给每个页面写一套单元测试。

**功能测试**是在Chrome中像真实用户一样操作整个流程，检查多个模块组合后是否可用，例如发布后能否搜索到、进入详情后能否正确返回、状态更新后其他页面是否同步。

### 10.3 自动单元测试清单

作业正文写至少5个用例；附录要求至少10个用例，并至少采用白盒设计方法，并非要求每个用例都只能用白盒方法。项目计划完成以下14项，正常测试与边界测试结合，状态服务按实际代码分支设计：

| 编号 | 测试内容 | 预期结果 |
| --- | --- | --- |
| T01 | 名称为空或全是空格 | 校验失败 |
| T02 | 名称30字和31字 | 30字通过，31字失败 |
| T03 | 日期为今天和明天 | 今天通过，未来日期失败 |
| T04 | 正确和错误手机号 | 分别通过和失败 |
| T05 | 创建寻物信息 | 状态为active，显示寻找中 |
| T06 | 创建招领信息 | 状态为active，显示待认领 |
| T07 | 空关键词搜索 | 返回全部信息并按时间排序 |
| T08 | 关键词、类型、类别组合搜索（含全部类别） | 返回同时满足条件的信息；全部类别不额外过滤 |
| T09 | 无匹配关键词 | 返回空数组，不抛异常 |
| T10 | 关闭寻物信息 | 显示已找到 |
| T11 | 关闭招领信息 | 显示已归还 |
| T12 | 非发布者修改状态 | 返回无权限，原数据不变 |
| T13 | 发布者再次关闭已完成记录 | 拒绝重复修改，记录和更新时间不变 |
| T14 | 关闭不存在ID的记录 | 返回不存在，不修改其他记录 |

成员A负责 T05-T14，成员B负责 T01-T04。两个人都必须在自己的电脑上执行全部测试；编号是测试计划，报告中以实际执行数量为准，不预先声称测试已经通过。

**白盒分支对应：** 对状态服务逐项覆盖 `记录不存在`（T14）、`存在但非本人`（T12）、`本人但已关闭`（T13）、`本人且未完成`（T10、T11）；T10和T11还验证两类中文状态映射。测试报告画出这些判断的控制流，并记录预期返回值、是否写入和数据是否改变。若实现增加了分支，例如保存失败，应相应补测试；此表不代表整个项目已经达到100%分支覆盖。

### 10.4 Chrome功能测试

两人交换测试，至少走完以下流程：

1. 发布一条寻物信息，在首页和“我的发布”看到它。
2. 发布一条招领信息，刷新页面后数据仍存在。
3. 输入关键词搜索，从结果进入正确详情，再返回原搜索结果。
4. 在file://页面复制联系方式并粘贴核对；模拟复制接口不可用或拒绝，检查手动复制提示和文本是否可选中。
5. 将寻物改为“已找到”，检查所有页面同步。
6. 将招领改为“已归还”，检查所有页面同步。
7. 提交空表单、搜索不存在关键词、访问不存在的详情ID，检查错误反馈。
8. 模拟存储读取或写入失败，检查不白屏、不误报保存成功，原数据和表单仍保留。

功能开发时在对应PR中说明验证步骤和结果；测试阶段由A将实际功能测试结果统一汇总到 `docs/测试报告.md`，写清测试步骤、预期结果、实际结果和是否通过，不为每个功能另建一份测试记录。

## 11. GitHub协作流程

1. 一位成员创建名为“第一个学号-第二个学号”的仓库。
2. 另一位成员 Fork 项目，并通过 Pull Request 提交功能。
3. 每个功能从最新 `main` 创建分支，例如：

```text
feature/a-search
feature/a-status
feature/b-publish-page
feature/b-detail-page
fix/home-layout
```

4. 一个功能完成且可以运行后至少提交一次。
5. Commit应说明实际内容，例如：

```text
feat(search): 支持关键词和类型筛选
feat(publish): 完成发布表单校验
fix(detail): 修复返回错误页面的问题
test(status): 增加寻物和招领状态测试
docs(readme): 补充运行说明
```

6. PR必须写明修改内容和测试方法，由另一人检查后合并。
7. 禁止使用“修改”“最终版”“111”等无法说明内容的Commit。

## 12. 界面与代码要求

- 保留第一次原型的蓝白校园风格、圆角卡片和底部导航。
- 蓝色表示主要操作，橙红色表示寻物，绿色表示招领。
- 文字、按钮和表单使用独立DOM，不能把整页做成背景图片。
- 底部导航不能遮挡页面内容。
- 卡片使用Flexbox或Grid，避免大量绝对定位造成重叠。
- 文件统一使用UTF-8，重点检查中文乱码。
- 用户输入使用 `textContent` 等安全方式显示，不能直接拼接进 `innerHTML`。
- 页面不能直接操作 `localStorage`，必须调用成员A编写的数据服务。
- 点击操作使用 `<button>` 或 `<a>`，不能用透明点击层。
